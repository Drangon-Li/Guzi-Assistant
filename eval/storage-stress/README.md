# 存储 / 检索压力测试（#路线图 1a / 1d）

验证所选「纯 TS 暴力余弦」记忆检索在规模下的**延迟 + 准确度**，给出「存储上限 / 检索效果」的真实数字：个人量级是否够用、何时需换 sqlite-vec / ANN。

真实 needle 记忆 + 真实查询走 relay 嵌入；distractor 用随机单位向量；规模 N=1k/5k/20k。

## 跑

```bash
node --max-old-space-size=2048 eval/storage-stress/run.mjs
```

## 基线结果（2026-06-15，text-embedding-3-small，1536 维）

| N(总记忆) | 建库(ms) | 单次检索 avg(ms) | top-1 | top-3 | 估算内存 |
|---|---|---|---|---|---|
| 1008 | 95 | **8.0** | 5/5 | 5/5 | ~12MB |
| 5008 | 307 | **21.2** | 5/5 | 5/5 | ~62MB |
| 20008 | 1060 | **88.6** | 5/5 | 5/5 | ~246MB |

## 结论

- **检索效果**：真实语义检索在 2 万条随机干扰里仍 **5/5 命中 top-1**，准确度不随规模下降。
- **延迟**：暴力余弦线性增长 ≈ 4.4ms/千条。1 万条 <45ms、2 万条 ~89ms，**个人量级（数年使用）体感无感**。外推 5 万条 ~220ms（仍可用），10 万条 ~440ms（偏慢）。
- **真瓶颈是内存/读取**：embedding 全量驻留 ~12MB/千条；且每次检索从 SQLite 读 + JSON.parse 全部向量才是规模下的实际开销 → 已加**内存向量缓存**（`memory.ts`，新增记忆失效）消除重复读解析。
- **存储上限**：纯本地暴力方案放心用到 **~2 万条记忆**（<90ms、满准确、~246MB）。再往上（>5 万）内存/延迟开始吃紧，届时再换 sqlite-vec / HNSW（设计已隔离在 `memory-extract.ts` 的 topK，替换面小）。SQLite 本身（WAL）存这点元数据毫无压力。

→ 对一个个人事项捕获工具，当前本地检索设计**容量与效果均充分**，无需引入原生向量库依赖（与 Win 优先、零 sidecar 一致）。
